# Terminal-Bench 2.0：多大 context/output 已有实跑证据

2026-10-16 联网核验，优先使用研究者自己的实验说明、原论文和官方模型卡；ego-browser 实际读取论文/作者页，web检索与源码读取补充。未运行任务、模型或API，未读取正式题答案；不改主协议。

**有直接证据说明32K context、每次4K输出能在完整TB2跑出有意义成绩，因此“终端任务一定要256K才有用”并不成立。但没找到同一Qwen3.6-35B-A3B、同Terminus-2、其余设置不变的32K→64K→128K→256K消融，无法量化我们降到32K会损失多少。**

## 1. 最直接的32K/4K实跑：AfterQuery

[AfterQuery作者实验文章，2026-03-31](https://www.afterquery.com/blog/how-we-improved-terminal-bench-2-with-tinker-and-harbor) 的页末明确给出：Terminal-Bench2.0完整89任务、Terminus-2、temperature=1、max output=4096、max context=32K、Pass@1取五次运行平均。正文还说明评测使用Terminus-2默认的不限turn、开启summarization；训练episode的20turn/无摘要限制不能混作评测设置。

| GPT-OSS-20B 阶段 | TB2成绩 | 公开评测预算 |
| --- | ---: | --- |
| Base | 3.1% | 上述32K context / 4096单次输出 |
| SFT | 13.5% | 同页公开评测设置 |
| SFT+RLVR | 17.0% | 同页公开评测设置 |

这是一手作者报告，支持“32K/4K可做完整、有区分度的agent评测”。**不是32K对256K的对照，也不是Qwen3.6成绩，不能拿17.0%预测我们分数。** 作者写的是max context32K，没有附可审计的服务启动参数或输入+输出长度校验实现；因此只能按其公开名称引用，不能声称本次已验证其32K严格如何扣除4096输出。我们的实现若用`max_model_len=32768`，则输入与输出共享32768，4K输出时实际prompt预算为28672。

## 2. 同Terminus-2、Qwen系的长度消融：40K并未输给64K

[Nemotron-Terminal作者论文 Table8、§5.5](https://arxiv.org/html/2602.21193v1#S5.SS5) 在Qwen3-8B上给出：

| SFT最大序列 | Eval最大序列 | SFT YaRN | Eval YaRN | TB2 |
| ---: | ---: | --- | --- | ---: |
| 32768 | 40960 | 否 | 否 | 13.0±2.2 |
| 32768 | 65536 | 否 | 是 | 11.9±2.0 |
| 65536 | 65536 | 否 | 否 | 10.3±2.0 |
| 65536 | 65536 | 是 | 是 | 11.9±2.1 |

注意 **32768是第一行SFT长度，评测实际是40960，不可说成32K评测13%**。不同设置还改变训练长度/YaRN，作者报告没有显著收益；不能据此证明context越短越好，更不能外推原生256K的Qwen3.6。

论文称多数其采集的训练轨迹能放进32768，但仍有不可忽略长尾；没有在正文给出32K/64K覆盖率百分比。这个统计属于合成训练轨迹，不是“TB2测试任务有多少都只需32K”，也不是单次输出长度分布。Table8没有明确列出每次输出cap，不能从40960减32768就臆造8192输出设置。

## 3. 128K/8K有更高成绩先例；当前同模型证据仍为256K/80K

| 来源 | 模型/agent | context / 输出上限 | 原版TB2成绩与边界 |
| --- | --- | --- | --- |
| [GLM-5官方卡](https://huggingface.co/zai-org/GLM-5/blob/main/README.md) | GLM-5 / Terminus-2 | 128K / 8192；2小时，16CPU/32GB | 56.2%。60.7%是修订verified任务集，不能混入原版；不是我们Qwen的受控对照。 |
| [固定Qwen3.6-35B-A3B卡](https://huggingface.co/Qwen/Qwen3.6-35B-A3B/blob/995ad96eacd98c81ed38be0c5b274b04031597b0/README.md) | 当前Base / Harbor-Terminus-2 | 256K / 80K；3小时，32CPU/48GB，五次均值 | 51.5%。未附32K/64K/128K降窗成绩。卡另建议复杂thinking场景至少保留128K，这是部署建议，不是降窗消融结果。 |

这些实例说明4K/8K单次输出并非“agent根本不能工作”的额度：agent可用多次较短动作推进任务；但长任务会累积历史，是否摘要、如何保存thinking、输出截断和超时都影响结果。模型/agent/量化/任务版本/资源不同的成绩，不能相减当作context的收益。

## 对本项目的判断

- **32K/4K可作为有文献支持的低成本开发候选**，尤其用于SFT/合版消融和工具行为诊断；证据强于“凭感觉32K一定够/一定不够”。
- 如果希望保留长任务能力而又避免80K单次长输出，**64K/8K是合理待测折中，128K/8K有公开高分先例**；目前没有一手证据足以断言64K是TB2普遍最优或已饱和。这里的64K建议是工程判断，不是上述论文已经证明。
- 对当前Qwen3.6，先比较独立dev的32K/64K（必要时128K），记录真实最大prompt、context失败/摘要次数、输出触顶和成功率，才能确定我们的“够用”。这不要求为消融重复正式TB全量。
- 本题正式TB仍按题定256K/80K执行；低预算结果单列。降低上限只会减少长尾计算/可能提高并发，同样短的请求不因上限变小自动加速，不能承诺8倍省时。

未找到：同Qwen3.6/Terminus-2且其他条件固定的长度消融、官方TB2逐任务运行所需context的可靠百分位表、证明80K单次输出是最小必要额度的消融。另检索到DeepSeek论文的“20%+超过128K”实际上属于search-agent评测，**不可引用成TB2分布**。[DeepSeek原文§4.1](https://arxiv.org/html/2512.02556v1#S4.SS1)
