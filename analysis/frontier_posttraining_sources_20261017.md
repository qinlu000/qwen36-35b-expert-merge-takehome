# 公开后训练方法与本项目的修复顺序

核实日期：2026-10-17。只使用下列团队自己的技术报告；这些是相关公开案例，不代表所有实验室当前的内部配方。本文未启动训练、模型推理、评分或 GPU 作业。

## 公开报告明确写了什么

| 团队与来源 | 与当前问题直接相关的做法 |
| --- | --- |
| [Qwen3 技术报告，§4.1–4.5、§4.7](https://arxiv.org/html/2505.09388v1) | Cold-start 先留独立验证题，过滤错误、明显重复及疑似验证相似的轨迹，并主张此阶段少样本、少步；thinking 与 non-thinking 使用明确模板和混合数据融合。Reasoning RL 控制 entropy 稳定或缓升；general RL 使用完整多轮真实环境反馈。小模型还使用学生自己生成序列、教师 logits 提供 KL 监督的 on-policy 蒸馏。报告逐阶段检查任务能力，部分能力仍会回落。 |
| [DeepSeek-R1 技术报告，§2.3–2.4、§5](https://arxiv.org/html/2501.12948v1) | 高质量 cold-start → reasoning RL → 拒绝采样与混合 SFT → general RL。SFT 数据约 60 万推理、20 万通用样本；蒸馏小模型可只做 SFT。报告承认 R1 的 function calling、多轮等弱于 V3，软件工程评测太慢限制了大规模 RL。因此“推理更强”不能直接推出“工具轨迹更适合”。 |
| [Kimi K2 技术报告，§3.1.1、§3.2.3](https://arxiv.org/html/2507.20534v1) | 用任务 rubric 筛选多轮轨迹；模拟环境覆盖失败与边界情况，代码与软件工程另用真实沙箱和单测提供可靠反馈。RL 中混入精选高质量样本的 PTX loss 以减轻遗忘，并控制每类任务的生成预算。它没有仅靠 teacher-forced loss 证明 agent 成功率。 |
| [DeepSeek-V3.2 技术报告，§3、§3.2](https://arxiv.org/html/2512.02556v1) | 专家先经过大规模RL，再生成领域数据蒸馏至最终模型，并继续混合RL；用不同模型分别生成thinking和non-thinking数据。工具链reasoning保留到新user才移除，工具观察到达时保留，报告明确讨论模拟user消息的agent框架边界。这里的专家蒸馏不是把专家权重直接平均。 |
| [Thinking Machines：On-Policy Distillation](https://thinkingmachines.ai/blog/on-policy-distillation/) | 指出静态教师轨迹让学生只见教师常见状态，自主生成的早期错误会累积；其方法是学生生成轨迹，教师给相同历史下逐token log-prob，按reverse KL构成反馈更新。教师补一个纠错答案再做SFT可以是数据改进候选，但不等于复现这套数值蒸馏。 |

这里的 entropy 控制属于 Qwen 报告的 **RL 阶段**；不能据此给我们的 SFT 盲加 entropy 奖励。Kimi 的 PTX 也属于其联合 RL 配方，不能写成已经证明某个 SFT 混合比例最优。上述报告没有提供一个适用于本项目 Qwen3.6 LoRA 的统一学习率或 entropy 系数。

## 对本项目的推论与建议（不是论文实验结论）

1. **先排除实现问题，再增加训练。** 我们已知一条真实 SWE 多轮样本的空 think 壳在训练/评测编码不同，单参数 CPU 对照可以使其一致；这还不能证明是 0/51 的唯一原因。应扩大到有代表性的多轮样本检查 token、监督 mask、当前生成前缀，再检查实际服务的适配器数值效果。不能只看 “Loaded adapter” 或正常下降的 loss。
2. **把“学会示范”与“自主完成任务”分开检查。** SFT 在教师给定的正确历史上预测下一步，部署后却会走到自己的错误状态；长轨迹中的早期偏离会累积。上述真实环境 RL/on-policy 方法说明大团队专门补这一环。我方短期不必上完整 RL，可在非正式测试任务上检查是否编辑、运行测试、识别报错、终止重复，而非增加一轮同样的离线 SFT。
3. **低 LR 是受控实验，不是已定位的根因。** 本项目峰值 1e-4、梯度有限、entropy 未记录。先统一编码，再固定数据与训练量比较原 LR 与保守候选 2e-5，才能隔离 LR；不能把“修模板+换数据+降 LR”同时做完后全部归因于 LR。若预算只够一版，可选保守候选，但只能报告联合修复效果。
4. **用少量可执行任务作工程准入，保留能力要实测。** 建议后续版本在不接触正式测试选择的前提下，检查重复动作、空 patch、有效工具调用、完成率及通用指令能力。固定输入的 entropy、top1、相对 Base 的 KL 可辅助定位；指标变好不替代真实成功率。这里是建议的新诊断门槛，不是恢复用户已取消的整套 task-level validation。
5. **轨迹选择不能只看教师名气或成功标签。** 需要兼顾任务覆盖、工具协议、预算、失败后纠错与真实执行证据；仅保留终局成功可用于 SFT，但不能据此保证学生在自生成错误历史上也能恢复。当前数据重复审计未发现训练集里有上百次连续同命令，不应把部署复读直接归咎于“原数据全是复读”。

适合当前资源的次序：编码/服务正确性 → 小规模同协议自主执行诊断 → 一版保守 SFT 修复 → 有证据后再扩大数据或设计纠错/on-policy 训练。正式 Base、专家、AVG64 的历史结果和冻结模型仍原样保留；此笔记不授权替换主模型或重跑正式答卷。
